## PRD

Build the localhost-only doctor portal that an internal reviewer (and, post-handoff, a real doctor) uses to review AI-extracted clinical claims for the 10 synthetic transcripts. Render the original transcript with **dual-layer highlights** (green for claim evidence, red for red-flag-rule matches without a corresponding urgent claim, per Appendix A.2). Render each claim as an audit card with all SPEC §8.8 fields and an `extractionType` badge (yellow for `interpretation`). Provide a Claim Edit Modal with the Appendix A.3 self-classification radio. End the flow with a filtered accepted-claims summary that replaces the cut report generator.

## Components (build in dependency order, tests-first)

1. **TranscriptPickerPage** (`app/page.tsx`) — list of 10 transcripts; clicking one navigates to the review page.
2. **ReviewPage** (`app/review/[id]/page.tsx`) — server-fetches `/analyze` for the selected transcript (Phase 2 integration; uses fixture in Phase 1).
3. **DualLayerInputView** — renders `rawText` with green spans (from `claim.evidence`) and red spans (from response-level `redFlagOnlySpans`). Both layers use char offsets into `rawText`. Handle nested/overlapping spans cleanly. Test: known input renders both layers without overlap glitches.
4. **AuditCard** — displays:
   - Claim text (and the corrected text + strikethrough overlay if edited)
   - Evidence (highlighted in the input view above; small inline quote in the card)
   - Confidence (% with a small bar)
   - Risk-level chip
   - `missingInfo` list
   - `safetyStatus` badge
   - **`extractionType` badge** — yellow with "interpretation, not direct quote" label for `interpretation`
     - **Hover/focus tooltip (post-eng-review M1a):** "Direct: claim text closely paraphrases the cited evidence span. Interpretation: the AI inferred this beyond what's directly quoted — review carefully." Plain English; no jargon. Accessible via keyboard focus, not just mouse hover.
   - `displayWarning` if present (e.g., "Low confidence — needs review")
   - Accept / Edit / Reject buttons
5. **ClaimEditModal** — original claim (read-only), evidence (read-only), editable corrected-claim textarea, **self-classification radio** with three options (`minor_wording` / `correction` / `external_knowledge_override`), reason textarea, Save (disabled until radio selected) / Cancel. On save, POST to `/review-claim` with `action="edited"`, `correctedClaim`, `doctorEditOrigin`, `reason`.
6. **AcceptedClaimsSummary** — shown after the reviewer reviews all claims for a transcript. Lists only `accepted` and `edited` claims with their final text. Does NOT include `pending` or `rejected`.

## Hard rules (no exceptions)

- **No internal-mode toggle. No debug overlays. No doctor-mode flag.** The portal looks and behaves identically for an internal reviewer and a future real doctor. The forward-compat guarantee is non-negotiable (pilot.md Appendix A).
- All copy is doctor-appropriate. **No "internal pilot" or "test mode" strings** anywhere in the UI. (Behind-the-scenes feature flags in code are fine; nothing visible in the rendered DOM.)
- Edits preserve `originalClaimText` server-side; the modal only sends `correctedClaim`. The portal never overwrites original text.
- The strikethrough overlay on changed words is shown in the AuditCard after save. The original evidence span stays highlighted regardless of edit type.
- The yellow `interpretation` badge is rendered for every `extractionType="interpretation"` claim, with the M1a tooltip attached. The reviewer must always be able to see which claims are inferred vs. directly extracted.
- **No confidence-filter UI in v1.** The audit card surfaces all claims with badges (`extractionType` yellow for interpretation, `displayWarning` for `confidence < 0.4`). A filter component would be premature — re-spec when a real doctor uses the portal in v2 (deferred to v2 backlog per pilot.md Appendix A).
